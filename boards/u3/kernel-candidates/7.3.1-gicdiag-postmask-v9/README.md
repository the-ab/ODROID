# U3 post-decision GIC diagnostic revision 9

[Deutsch](README.de.md)

Private diagnostic candidate `7.3.1-odroidu3-v9`, based on the pinned v3 server profile. In contrast to v8 it removes the four additional pre-disable MMIO reads and leaves `gic_dist_init()` byte-identical to the baseline. `gic_get_cpumask()` keeps its original reads, decision and critical warning in the original order; the added diagnostic call runs immediately before the unchanged return. No target mask or routing write is changed. The `GICPOST` lines report the original selected mask and subsequent read-only identification/target state.

V8 booted warm three times without the sporadic error. That does not establish a correction: sampling, output and code layout can affect timing. This revision separates pre-decision sampling from later observations. Neither diagnostic candidate is a release replacement. Use matching boot-file rollback and local UART capture. Default images/APT and firmware remain unchanged. Build and native outcomes require separate evidence.

Native diagnostic result (2026-11-02): the preceding v3 baseline warmboot succeeded. The first v9 warmboot selected masks `01,01,02,04,08` with no zero-mask warning and activated four CPUs at 0.299396 seconds. It then reported a PMIC I2C bus-idle timeout and regulator-enable failure, followed by an RCU CPU0 timer/scheduling stall; CPU0 did not answer the diagnostic NMI and userspace/SSH was not reached. The private UART trace is retained. Correct startup target masks therefore do not establish healthy later interrupt/timer handling. The I2C message may be a consequence of that failure; it is not yet proven to be the root cause. No IRQ-routing fix is claimed. The same v9 binary and arguments booted normally after a user power cycle: four CPUs, no PMIC timeout/RCU stall, no kernel journal errors, no failed units and no taint. The original v3 extlinux/uImage were then restored byte-for-byte; the running kernel remained v9 until a subsequent explicitly marked comparison boot.

A short comparison used the unchanged v3 binary with `nohlt` plus the same serial diagnostic arguments. Two warmboots reached healthy userspace, with four CPUs, no GIC/PMIC/RCU error, no failed units or taint, and sampled CPU temperatures of 48 and 47 degrees Celsius. `CONFIG_GENERIC_IDLE_POLL_SETUP=y` makes `nohlt` bypass the architecture idle handler and busy-poll; this temporary diagnostic increases idle power. The original boot arguments were restored after the comparison. The sample is too small to establish an idle-path defect or a correction. No release uses this parameter.

The subsequent ordinary v3 warmboot, after exact restoration of the original extlinux/uImage, again emitted the original early `GIC CPU mask not found` error. This is an A/B observation across an intermittent fault, not proof that busy-polling repairs the reset/interrupt state. This ordinary boot nevertheless reached userspace/SSH with four CPUs, no failed units or taint, and a sampled temperature of35 degrees Celsius. One GIC error remains in its boot journal. The warning alone does not establish a failed boot; conversely, its absence did not prevent the v9 CPU0 stall. Normal v3 boot files and arguments are now active, without nohlt; no further reboot is part of this comparison.
