# U3 I2S and USB investigation

[Deutsch](I2S-USB.de.md)

Current v32 qualification: the reviewed audio/optional-USB fixes from v7 are retained together with the targeted GIC RAM-counter base-selection correction and seven io_uring backports. The DTB is byte-identical to v7. Ten pure warmboots and five controlled halt/cold starts with normal release arguments pass; four CPU timers and all 351 module hashes match at every boot. The former RX-DMA and missing optional-VBUS warnings are absent. An internal stereo codec loop and real HSIC/Ethernet transfer pass. The subsequently observed TUN softirq-statistics warning is corrected by three short bottom-half guards and the native VPN/full-server comparison now passes with lockdep enabled. The exact original GIC text-patch/cache mechanism remains unproven; no new firmware or complete physical-peripheral acceptance is claimed. Earlier controls below remain historical.

The [revision 7 candidate](../boards/u3/kernel-candidates/7.3.1-i2s-usb-v7/README.md), Linux `7.3.1-odroidu3-v7` / DEB `7.3.1-8`, is **not qualified for release**. Its second self-restart hung. Public APT packages remain v3 and the 1.0.2 image files/defaults are unchanged.

The USB PHY binding makes `vbus-supply` optional, while the driver used mandatory regulator acquisition. The fix requests an optional supply, accepts only ENODEV as absence and propagates real errors/probe deferral. It adds no fake regulator and does not join the shared PHY to the independently switched OTG rail. Native USB Ethernet, hub and HID enumeration work. On v7, a 16 MiB transfer in each direction through USB Ethernet matched SHA256 with zero RX/TX interface errors; RX-dropped increased by four. The earlier v4 run had six RX drops. Neither result is described as zero packet drops. Unused USB storage and OTG roles are not blanket-qualified.

The primary I2S TX and RX channels already existed. A secondary software playback PCM also eagerly requested primary RX. The wrapper now requests only the attached stream using its actual CPU DAI's DMA name. Primary/legacy paths remain. Secondary functionality is not disabled to hide a warning. Native DMA state shows the primary TX/RX owners without duplicate allocation. V7 restores the upstream secondary-device topology; `i2s.c` is byte-identical to upstream. Removing the parent relationship added in v4 did not resolve the warm-start failure.

Capture tests exposed a missing backend route and a microphone connected to a headphone sink/IN1 instead of a microphone source and the selected IN12 preamp. A Mic Jack widget now connects MICBIAS and IN12 to capture. DAPM powers the bias, preamp, ADCs and I2S recording path. The HDMI transmitter also incorrectly advertised capture, reserving hdmi-codec's single stream and blocking analog full duplex; `no_i2s_capture` now describes its actual capability.

Native internal codec loopback on v6 and v7 at 48 kHz/S16 stereo returned the separate 400 Hz/600 Hz channels with over 99.9999% reference-tone energy and negligible cross-channel energy. The user accepted headphone playback on v4 and v6. Quiet v7 playback completed. The unverified headset produced no intelligible recorded voice, so physical microphone acceptance remains open. Test recordings were deleted and the mixer restored.

Host resource checks execute the changed C wrapper/regulator logic with API stubs, inspect the compiled DT capture graph, HDMI capability and actual secondary-device construction. ARM compilation, the unchanged 101-capability server gate and 23 package/boot protection tests are separate evidence. All 95,979 upstream regular files were compared for v7: 95,971 unchanged, exactly eight documented modifications. The config differs from v3 only in LOCALVERSION. All 351 modules and installed boot payload hashes matched on the board.

Warm-start comparison: v3 passed two self-restarts and one after 48 kHz playback. V4 failed after playback; the user reported very rapid LED blinking. V6 had two failures requiring power cycles, with a successful restart between them. V7 booted initially; its first self-restart returned but logged `GIC CPU mask not found - kernel will fail to boot.` Its next self-restart hung. A power cycle booted the unchanged v7 payload with no journal errors. LED states do not establish a panic or identify the failing boot stage.

After the GIC warning, all four CPUs were online and interrupt delivery operated. Read-only inspection of the non-banked GIC windows, including the DT's 0x4000 CPU offset, found masks 1, 2, 4 and 8. This later state does not explain or invalidate the early warning. No IRQ mask was invented, no live register was written and no warning was suppressed. The final shutdown journal and empty pstore do not locate the failure after logging stops. The added I2S parent is not established as the cause; v7 demonstrates that reverting it is insufficient.

The eMMC hardware reset was already enabled (`RST_N_FUNCTION=0x01`), pwrseq_emmc is bound and the active-low reset GPIO is correctly owned/high. No EXT_CSD setting or boot0/boot1 content was changed. Preserve the verified v3 fallback and same-medium backup. Further early-boot diagnosis needs a captured console trace; a U3-compatible UART must respect the manufacturer's [1.8 V interfaces](https://www.hardkernel.com/shop/odroid-u3/). Board-specific connector and pinout must be checked before connection.

These are local reviewed fixes, not claimed upstream acceptances. The functional I2S/USB results do not qualify an unstable kernel for public APT or new images. Matching sources, configs, recipes, exact packages and verified debug-build archives are retained. References include the [optional regulator API](https://docs.kernel.org/driver-api/regulator.html) and the exact upstream bindings/drivers in the matching sources.

## UART follow-up (2 November 2026)

Complete early serial output also reproduced a failure with the unchanged v3 kernel: two GIC CPU-mask warnings before secondary-CPU startup, all CPUs up only after4.076 seconds and no RCU Tasks Trace callback or login. A manual cold start with the same kernel and arguments had no GIC warning, all CPUs up after0.234 seconds and both RCU callbacks. The original boot configuration was restored after recovery. This supersedes the assumption that the older successful v3 restarts establish a reliable hardware fallback. Preserve its files and the matching backup, but do not claim boot reliability or an I2S-specific cause.

The separate [v8 diagnostic profile](../boards/u3/kernel-candidates/7.3.1-gicdiag-v8/README.md) adds read-only early GIC register output on the v3 baseline. It is instrumentation, not a routing fix or a released replacement.


The [v9 post-decision profile](../boards/u3/kernel-candidates/7.3.1-gicdiag-postmask-v9/README.md) removes the additional pre-mask sampling. Its first warmboot nevertheless stalled after valid masks1/2/4/8: a PMIC I2C timeout preceded an RCU/timer stall on CPU0, which did not answer a backtrace IPI. The same binary/arguments booted normally after a power cycle. Two short v3/nohlt warmboots succeeded; after removing this temporary busy-poll parameter, normal v3 reached userspace despite one early GIC warning. Neither the warning alone nor its absence predicts the complete outcome.

A separate comparison restored the earlier Linux6.12.114-v1 package on the same Ubuntu installation and boot firmware; its DTB is byte-identical to the v3 baseline. Two recorded warmboots reached userspace with four CPUs and no GIC/PMIC/RCU or kernel-journal error. The auditd/audit-rules units failed because this old profile lacks CONFIG_AUDIT; it is a hardware baseline, not a replacement for the server profile. Healthy read-only GIC control/priority/identity and private target values matched across both kernel bases. Versions and configurations differ, and two successes cannot isolate a regression or exclude intermittent board/PSU failure. The original v3 boot files and arguments were restored afterwards. Matching binaries, configurations, traces and module-verified fallback remain available; no new public binary or firmware change results from these comparisons.

Targeted pinned-source comparison found byte-identical central GIC mask/distributor/CPU-interface/IPI functions, ARM restart and Exynos SMP files, watchdog restart/shutdown functions and Exynos4 PMU data. Timer hotplug teardown and CPU-clock code have changes requiring call-path evidence; newer GS101 CPU-power hooks are not enabled by the Exynos4412 data. No source difference is treated as a proven correction. The return boot into normal v3 completed with zero kernel-journal errors, no failed units, active audit with no lost events and advancing timer counts on all four CPUs.

## Extended same-eMMC comparison (3 November 2026)

The retained Linux `6.12.114-odroidu3-v1` completed ten consecutive same-kernel warmboots on the test eMMC, in addition to the transition boot. The eMMC, Ubuntu installation, bootloader and DTB were the same as for v17; the DTB matched byte for byte. Every boot had four online CPUs, advancing timer counts on every CPU, matching boot/module/configuration payloads, no kernel-journal errors and no unexpected failed services. UART slices and distinct boot identities were verified for all ten boots. No power cycle was needed during this series.

The two audit services failed as expected because this retained kernel lacks `CONFIG_AUDIT`; these failures were recorded explicitly. The old profile has 140 modules rather than 351 and also lacks PSI and some later enabled Cortex-A9 workarounds. This compares both kernel version and configuration. It supports a difference between the tested stacks, but does not isolate a source regression, prove a hardware fault absent, or qualify 6.12 as the server release. The exact normal v17 boot files and management state were restored afterwards; the return boot passed all 351-module, four-CPU, timer, journal, service and active-audit checks.

A separate v17 control changed only the selected boot argument to [`maxcpus=1`](https://docs.kernel.org/admin-guide/kernel-parameters.html), keeping the compiled SMP kernel, modules and DTB unchanged. The first transition boot stalled before userspace; UART confirmed one active CPU and ended after the 5.373-second AppArmor message. The planned five-warmboot series was not started. A subsequent cold recovery after a verified 10.038-second AC-relay OFF interval reached userspace with one CPU and passed the payload, timer, journal, service and active-audit checks. Limiting startup to one CPU therefore does not reliably avoid a start failure. This trace lacks an independent observer CPU and does not prove the stopped instruction or that this failure has exactly the same cause as the four-CPU stalls. Startup timing and power consumption also change in this control. The normal boot configuration was restored. The final return to four-CPU v17 also passed the native payload, timer, journal, service and active-audit checks.

## I²C interrupt controls (4 November 2026)

Three independent opt-in controls derived from v17 reproduced the start failure: [v19](../boards/u3/kernel-candidates/7.3.1-i2c-sync-v19/README.md) waited for IRQ completion before transfer clock-off; [v20](../boards/u3/kernel-candidates/7.3.1-i2c-clockhold-v20/README.md) retained an extra balanced clock reference; [v21](../boards/u3/kernel-candidates/7.3.1-i2c-poll-v21/README.md) used the existing polling path without registering I²C0's IRQ handler. V19 failed its first transition; v20 passed the transition and one pure warmboot, then failed the second. V21 passed the transition and four pure warmboots, then failed the fifth. All healthy candidate boots passed matching payload/module, timer, PMU, audit, journal and service checks; polling boots also verified successful RTC transfers with no I²C0 IRQ handler.

V21's late snapshot had I²C0 INTID90 disabled and not active, but MMC INTID109 active. I²C0 interrupt delivery is not required for that hang, so an explanation restricted to its IRQ handler does not cover all observed failures. The active interrupt is an observation, not a proven cause; the precise stopped CPU instruction remains uncaptured. Polling changes scheduling and latency and is not an accepted workaround. The general CPU/interrupt entry-return path needs further controlled evidence. A report-budget admission defect allowed only one late register dump when three watchdog calls coincided; skipped concurrent calls must not be treated as completed snapshots. No firmware, public APT or image default is promoted by these tests.

## Complete snapshots and a secondary MMC error path

The [v22 observer](../boards/u3/kernel-candidates/7.3.1-diag-budget-v22/README.md) fixes report admission under concurrent watchdog calls. Native failure now yielded three complete numbered late dumps with an unchanged CPU0 timer count and active I²C0 INTID90. A later CPU3 BUG resolved to the regulator range check via the MMC VQMMC caller, after I²C failures.

The [v23 correction](../boards/u3/kernel-candidates/7.3.1-mmc-regulator-v23/README.md) rejects inverted voltage ranges and propagates negative supported-voltage query errors before voltage APIs. Sixteen host cases passed against the actual MMC code. The helper is byte-identical in the older 6.12.114 source, so this is not established as a new Linux7 regression. Transition and one pure warmboot passed, with fixed supply readbacks 1.8V/2.8V; the second pure warmboot and first cold recovery still hung. Both supplied three complete late snapshots and no kernel BUG in their captures. This fixes an identified secondary error path; it is not an accepted solution to the initial CPU0 stall. Native error-path coverage, boot reliability and binary release acceptance remain separate claims.

Further CPU/GIC observation uses the separate [v24 diagnostic ordering candidate](../boards/u3/kernel-candidates/7.3.1-gic-order-v24/README.md); native outcome remains separate.

V24 reached userspace and passed full native health, then its first pure warmboot stalled with three completed reports. Diagnostic ordering did not fix the CPU0 stall. Shared-priority raw values require non-banked-alias/security-view controls before interpretation; see the candidate report.
